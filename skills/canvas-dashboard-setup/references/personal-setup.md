# Personal local testing: browser + hidden terminal

This is a user-requested, single-user local testing path. Canvas documents manual tokens for testing and requires OAuth for applications used by multiple users. Do not market this path as policy-compliant multi-user onboarding. Tokens can have write permissions even though the scripts query GET endpoints only. Never collect tokens for the maintainer or a shared server.

1. Clone/reuse the repository; npm ci; npm run setup. Detect the OS and available browser/terminal tooling yourself. Do not ask the user to type installation/configuration commands the agent can execute safely.
2. Open https://canvas.nus.edu.sg/profile/settings using the user's authenticated browser; for another institution use the configured, user-authorized Canvas origin. Let the user complete login/MFA if needed. Locate Approved Integrations / New Access Token from current visible page state.
3. If stored credentials already exist, first try `npm run canvas:resume` without opening a new token dialog. It syncs/builds/starts using the stored token; do not generate a replacement unless the user requests it or approves reauthorization after failure. Otherwise launch `npm run canvas:connect` from the checkout via the agent's command tool. It opens a separate **visible native terminal**, with hidden input; no secret is passed to the command tool. Read only `.local/token-input-status.json`, never credential files. If native launch is unavailable, ask the user to run `npm run canvas:token` in their own terminal; do not accept a token in chat or an agent tool PTY.
4. Open the New Access Token dialog, set a descriptive purpose such as `Canvas dashboard personal testing` and propose a short expiry (e.g. 30 days). Explain that the token may carry broader rights than this read-only app. Before clicking Generate Token, ask for action-time confirmation of purpose/expiry and local storage/use. If browser tooling prohibits performing that action, the user clicks Generate instead. Do not create a new token when a working stored one already exists and the user has not requested replacement.
5. After generation, **do not take snapshots/screenshots, read token text, inspect clipboard contents, or send it to the model**. Hand off for the user to copy the displayed token and paste into the already-open terminal. The helper validates the token against the configured origin with a GET profile request, discards profile data, and saves encrypted credentials only after success. The status receipt contains no token or profile.
6. After token entry, the native helper automatically performs sync, build, local loopback start and HTTP readiness verification. Observe the receipt's `verified` → `syncing` → `building` → `starting` → `ready` sequence; **do not start duplicate sync/build/server commands while this is running**. On `ready`, open its URL and check desktop/mobile rendering and actual source freshness. Inspect .local/last-check.json for unavailable sections and course changes. Run npm test if not already checked. If `failed` or `launch-failed`, report that single blocker; a bootstrap failure can be retried with npm run canvas:resume without generating another token. If `waiting`, request only token entry and use the product's supported wait/continuation mechanism. Do not reread the generated token page.
7. Clear the clipboard yourself only if the user asks or authorizes it; otherwise recommend the user clear it and close the token page. Token expiry/revocation requires the same visible flow again; personal tokens cannot be refreshed with OAuth. Never auto-generate replacements or grant new permissions during unattended monitoring.

No real student token is required to test the repository. Unit tests use dummy values and injected responses. Native terminal and real Canvas UI behavior must be verified on the target machine; unit tests alone do not establish that end-to-end behavior works.
